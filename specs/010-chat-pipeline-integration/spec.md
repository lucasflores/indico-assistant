# Feature Specification: Chat Pipeline Integration

**Feature Branch**: `010-chat-pipeline-integration`  
**Created**: 2026-01-18  
**Status**: Closed  
**Input**: User description: "Get the widget fully functioning with a real LLM API backend. This includes the verified functioning of the NL2SQL component. The current status is a broken widget that simply echoes back the user's message because the chat flow drops into the mock path when _process_with_nl2sql raises an ImportError. We want our full pipeline (chat interface) working by the end of implementation."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Send Query and Receive LLM Response (Priority: P1)

As a user with the chat widget open, I want to type a natural language question and receive an intelligent response from the LLM, so that I can get information about Indico events and data.

**Why this priority**: This is the core functionality - without a working LLM response, the widget provides no value. Everything else depends on messages flowing through the real pipeline.

**Independent Test**: Can be fully tested by opening the widget, typing "What events are happening this week?", and receiving a contextual response (not an echo or mock message). Delivers the primary value of AI-assisted event discovery.

**Acceptance Scenarios**:

1. **Given** the chat widget is open and the user is authenticated, **When** the user types "Hello, what can you help me with?", **Then** they receive a helpful response describing the assistant's capabilities (not an echo of their message)
2. **Given** the LLM service is properly configured, **When** the user sends a message, **Then** the response is generated by the actual LLM (no "mock_response: true" in metadata)
3. **Given** the user sends a query, **When** the backend processes it, **Then** the processing uses the NL2SQLPipeline component (not a fallback)

---

### User Story 2 - NL2SQL Query Execution (Priority: P1)

As a user, I want to ask questions about Indico data in natural language and have them translated to database queries, so that I can retrieve specific information without knowing SQL.

**Why this priority**: The NL2SQL pipeline is the differentiating feature of this assistant. Without it working, users only get generic chat responses without access to actual Indico data.

**Independent Test**: Can be tested by asking "How many events are scheduled for next month?" and receiving a response that includes actual count data from the database. The response metadata should show `sql_generated` was populated.

**Acceptance Scenarios**:

1. **Given** the NL2SQL pipeline is functioning, **When** the user asks "How many events are there?", **Then** the system generates valid SQL, executes it, and returns the count
2. **Given** a data query is submitted, **When** processed through the pipeline, **Then** the response metadata includes `sql_generated` and `confidence` fields
3. **Given** the chat service attempts to process a query, **When** importing NL2SQL components, **Then** no ImportError is raised and the real pipeline is used

---

### User Story 3 - Chainlit Backend Integration (Priority: P1)

As a system operator, I want the Chainlit app to forward messages to the Indico plugin's chat API, so that messages flow through the complete backend pipeline instead of being echoed.

**Why this priority**: The Chainlit app is the bridge between the widget and the backend. If it just echoes messages, none of the LLM or NL2SQL functionality is accessible.

**Independent Test**: Can be tested by sending a message through the Chainlit interface and verifying (via logs or response content) that it was processed by the Indico chat endpoint, not the echo handler.

**Acceptance Scenarios**:

1. **Given** the Chainlit app receives a user message, **When** processing the message, **Then** it calls the Indico plugin's `/api/assistant/chat` endpoint (not echo)
2. **Given** the user is authenticated via JWT, **When** the message is sent to the backend, **Then** the user context (ID, permissions) is preserved
3. **Given** the backend returns a response, **When** displayed in the widget, **Then** the response content matches what the LLM/NL2SQL pipeline generated

---

### User Story 4 - Error Handling and Graceful Degradation (Priority: P2)

As a user, I want to receive helpful error messages when something goes wrong, so that I understand the issue and can take appropriate action.

**Why this priority**: Once the happy path works, robust error handling ensures users aren't confused by cryptic failures. This is essential for production readiness but secondary to core functionality.

**Independent Test**: Can be tested by temporarily disabling the LLM API key and sending a message, verifying the user receives a clear error message (not a stack trace or empty response).

**Acceptance Scenarios**:

1. **Given** the LLM service is unavailable, **When** the user sends a message, **Then** they receive a clear error message like "The assistant is temporarily unavailable"
2. **Given** the NL2SQL pipeline fails to generate valid SQL, **When** error correction is exhausted, **Then** the user receives a helpful message explaining the query couldn't be processed
3. **Given** any backend error occurs, **When** the error propagates to the widget, **Then** the error is displayed gracefully (no raw JSON or stack traces)

---

### User Story 5 - Session Persistence Across Messages (Priority: P2)

As a user having a conversation, I want my previous messages to provide context for follow-up questions, so that I can have a natural multi-turn conversation.

**Why this priority**: Conversation context significantly improves user experience but the assistant is still useful without it. Core message processing must work first.

**Independent Test**: Can be tested by asking "What events are next week?", then following up with "Show me the first one" - the second query should understand "the first one" refers to results from the first query.

**Acceptance Scenarios**:

1. **Given** a user has sent multiple messages in a session, **When** they send a follow-up question, **Then** the context from previous messages is included in the LLM prompt
2. **Given** a session exists, **When** the user returns to the widget, **Then** their session_id is preserved and conversation continues
3. **Given** conversation context is available, **When** processing a query, **Then** pronouns and references (e.g., "that event", "the first one") are resolved correctly

---

### Edge Cases

- What happens when the user sends an empty message? → System should reject with validation error
- How does the system handle very long messages? → Should truncate or reject gracefully with size limit
- What happens if the JWT token expires mid-session? → Should prompt re-authentication, not fail silently
- What happens when the database connection is lost? → Should return service unavailable error
- What happens with SQL injection attempts? → NL2SQL validator should reject malicious patterns
- What happens when the LLM returns malformed responses? → Pydantic validation catches and retries/fails gracefully

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST route messages from the Chainlit widget to the Indico chat API endpoint (`/api/assistant/chat`)
- **FR-002**: System MUST process chat messages through the NL2SQLPipeline (not NL2SQLService which doesn't exist)
- **FR-003**: System MUST generate responses using the configured LLM provider (Azure OpenAI, OpenAI, or vLLM)
- **FR-004**: System MUST return LLM-generated responses to the widget (no echo or mock responses in production)
- **FR-005**: System MUST preserve user authentication context when forwarding requests from Chainlit to Indico
- **FR-006**: System MUST include conversation history when building context for the LLM
- **FR-007**: System MUST handle import errors gracefully without falling back to mock responses when services are properly configured
- **FR-008**: System MUST return response metadata including `sql_generated`, `confidence`, and `data_sources` when applicable
- **FR-009**: System MUST validate user permissions before executing queries (via existing permission filtering) — *inherited from 003-nl2sql-pipeline, no new implementation required*
- **FR-010**: System MUST log pipeline execution stages for debugging and observability

### Key Entities

- **ChatMessage**: User or assistant message with content, metadata, and session reference
- **ChatSession**: Conversation container with user ownership and optional event scope  
- **NL2SQLPipeline**: Orchestrator for query classification → SQL generation → validation → execution → formatting
- **LLMService**: Abstraction layer for LLM provider interactions with structured output parsing

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Users receive intelligent, contextual responses to their queries (not echoes or "NL2SQL pipeline is not configured" messages)
- **SC-002**: Data queries return actual database results with generated SQL visible in metadata
- **SC-003**: End-to-end message latency p95 is under 10 seconds for typical queries (simple SELECT, <1000 rows); complex SQL operations may exceed this
- **SC-004**: 90% of well-formed natural language queries about events are successfully processed without errors (well-formed = grammatically correct English questions about events, registrations, or schedules; excludes ambiguous pronouns without prior context)
- **SC-005**: All messages flow through the authenticated pipeline with user context preserved
- **SC-006**: System gracefully handles errors with user-friendly messages (no raw exceptions shown to users)
- **SC-007**: Conversation context is maintained across multiple messages in the same session

## Assumptions

- The LLM provider (Azure OpenAI/OpenAI/vLLM) is properly configured with valid API credentials
- The database schema is accessible and the schema context file is present
- JWT authentication between Chainlit and Indico plugin is properly configured
- The Chainlit server and Indico plugin are running and network-accessible to each other
- User has appropriate permissions to access the events/data they're querying
- Chainlit communicates with Indico via direct HTTP calls to the REST API (`INDICO_API_URL` environment variable), forwarding the user's JWT token in the Authorization header

## Out of Scope

- New LLM features or model training
- UI/UX changes to the chat widget appearance (covered by 008-chat-widget, 009-chat-widget-styling)
- Vector search/RAG functionality improvements (covered by 006-vector-search-rag)
- Performance optimization beyond basic functionality
- Mobile-specific widget behavior

## Implementation Notes (Actual Changes Applied)

The following changes were required to make the pipeline work end-to-end. These are the authoritative changes that should be regenerated from the spec when re-implementing.

### Chainlit bridge (Chainlit → Indico API)
- Forward requests to `/api/assistant/chat` over HTTP using `httpx.AsyncClient` and preserve the Indico JWT.
- Use `X-Assistant-Auth` header for assistant API authentication.
- Persist the Indico `session_id` in Chainlit user session and include it on subsequent requests.
- Load `INDICO_API_URL` from environment or `chainlit_app/.env`.
- Store original JWT in Chainlit user metadata and session for re-use.
- Add user-friendly error handling for 401/403/422/5xx responses.
- Add optional SQL debug output behind `CHAINLIT_DEBUG_SQL` to surface generated SQL and metadata.
- Files: [chainlit_app/app_chnlit.py](chainlit_app/app_chnlit.py), [chainlit_app/requirements.txt](chainlit_app/requirements.txt), [chainlit_app/.env.example](chainlit_app/.env.example), [chainlit_app/README.md](chainlit_app/README.md)

### Indico assistant API auth and routing
- Accept `X-Assistant-Auth` for assistant API requests and log auth diagnostics.
- Disable CSRF checks for assistant API endpoints.
- Files: [indico_assistant/controllers/base.py](indico_assistant/controllers/base.py)

### LLM service fixes and diagnostics
- Pass `model` in all LLM calls and health checks.
- Normalize OpenAI-compatible `base_url` to include `/v1`.
- Use HuggingFace router base URL by default.
- Improve error mapping to surface `ValueError` messages.
- Add backward-compatible `LLMResponse.data` alias for `result`.
- Add `confidence` to `QueryClassification`.
- Files: [indico_assistant/services/llm/service.py](indico_assistant/services/llm/service.py), [indico_assistant/services/llm/factory.py](indico_assistant/services/llm/factory.py), [indico_assistant/services/llm/errors.py](indico_assistant/services/llm/errors.py), [indico_assistant/services/llm/models/base.py](indico_assistant/services/llm/models/base.py), [indico_assistant/services/llm/models/classification.py](indico_assistant/services/llm/models/classification.py)
