# Feature Specification: NL2SQL and Vector Search Prompt Optimization

**Feature Branch**: `013-nl2sql-prompt-optimization`  
**Created**: January 19, 2026  
**Status**: Draft  
**Input**: User description: "Improve NL2SQL and vector search LLM prompting approach based on reference implementation patterns. Investigate if guardrails are too restrictive."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Query Events with Rich Context (Priority: P1)

A user asks natural language questions about events/meetings and receives comprehensive, well-formatted results that include event IDs, titles, dates, timezones, and relevant contextual information.

**Why this priority**: This is the core functionality of the assistant. Users must be able to query events effectively with results that provide actionable information (event_id for linking, properly formatted dates/times, timezone awareness).

**Independent Test**: Can be fully tested by asking "What events are happening this week?" and verifying the response includes event IDs, properly formatted dates with timezone, and relevant contextual fields.

**Acceptance Scenarios**:

1. **Given** the user asks about upcoming events, **When** the query is processed, **Then** the results include event_id, event_title, event_start_dt (formatted as human-readable date/time), and event_timezone
2. **Given** the user asks about a specific event, **When** results are returned, **Then** additional context fields (description, venue, room, contributors) are included where relevant
3. **Given** the user asks about events using vague time references like "recently" or "this week", **When** the query is classified, **Then** PostgreSQL date functions are used to determine the time range rather than hardcoded dates

---

### User Story 2 - Query Contributor and Speaker Information (Priority: P1)

A user asks questions about who presented at events, who contributed talks, or speaker affiliations and receives properly joined results from multiple tables with aggregated contributor information.

**Why this priority**: Multi-table JOINs for contributor queries are a common use case. The reference prompt shows this requires complex aggregation with STRING_AGG and proper person/contribution linking.

**Independent Test**: Can be tested by asking "Who spoke at event X?" and verifying the response includes speaker names, affiliations, contribution titles, and descriptions with proper data aggregation.

**Acceptance Scenarios**:

1. **Given** the user asks about speakers for an event, **When** the SQL is generated, **Then** it properly JOINs contributions, contribution_person_links, and persons tables
2. **Given** multiple contributors exist for an event, **When** results are returned, **Then** contributor data is aggregated into a readable format (not duplicated rows)
3. **Given** the user asks about speakers, **When** the query executes, **Then** relevant fields like is_speaker, affiliation, email, and contribution details are included

---

### User Story 3 - Query Document Content with Vector Search (Priority: P2)

A user asks questions about the content within uploaded files (PDFs, slides, presentations) and receives relevant excerpts retrieved via vector similarity search **as part of a unified SQL query**.

**Why this priority**: Vector search (RAG) is a key differentiator for the assistant. The reference prompt shows a specific pattern using `embeddings <=> :query_vector` that must be generated by the LLM as part of the SQL query, not as a separate retrieval step.

**Independent Test**: Can be tested by asking "What does the presentation say about X?" and verifying the generated SQL includes `ORDER BY embeddings <=> :query_vector` against `extracted_documents` table.

**Acceptance Scenarios**:

1. **Given** the user asks about document content, **When** the LLM generates SQL, **Then** the query includes `ORDER BY embeddings <=> :query_vector` pattern targeting `plugin_assistant.extracted_documents`
2. **Given** a document content query is generated, **When** SQL is executed, **Then** the `:query_vector` parameter is substituted with the actual embedding of the user's query
3. **Given** the SQL returns document chunks, **When** results are formatted, **Then** `extracted_content` (or `content_text`) from the most similar chunks is included in the response

---

### User Story 4 - Query Attachments and Materials (Priority: P2)

A user asks about files, materials, or attachments associated with events or contributions and receives metadata and file references.

**Why this priority**: Attachment queries require specific JOIN patterns through folders → attachments → files tables that differ from event queries.

**Independent Test**: Can be tested by asking "What files are attached to event X?" and verifying file storage IDs, filenames, and contributor associations are returned.

**Acceptance Scenarios**:

1. **Given** the user asks about event materials, **When** the query is generated, **Then** it properly joins folders, attachments, and files tables with the correct event_id filtering
2. **Given** contributions have attachments, **When** queried, **Then** the attachment-to-contribution relationship is properly resolved
3. **Given** the user asks for PDFs or slides, **When** results are returned, **Then** storage_file_id or relevant identifiers are included for file retrieval

---

### User Story 5 - Relaxed Query Flexibility (Priority: P3)

A user's query that may benefit from CTEs, subqueries, or window functions is handled gracefully by generating alternative SQL patterns rather than failing.

**Why this priority**: Current guardrails may be too restrictive for legitimate analytical queries. The system should attempt to generate equivalent functionality within safe constraints.

**Independent Test**: Can be tested by asking "What are the top 5 events by registration count?" and verifying the system generates valid SQL (even without window functions) or explains the limitation.

**Acceptance Scenarios**:

1. **Given** a query that would naturally use a CTE, **When** the SQL generator processes it, **Then** it generates an equivalent query using JOINs or simpler patterns
2. **Given** a ranking query is requested, **When** processed, **Then** the system uses ORDER BY + LIMIT instead of window functions where possible
3. **Given** a query cannot be satisfied within guardrails, **When** this is detected, **Then** a helpful explanation is returned rather than a cryptic error

### Edge Cases

- What happens when the user references entities from previous conversation turns (co-reference resolution)?
- How does the system handle queries spanning multiple events without specific event_id constraints?
- What happens when vector search returns no similar documents?
- How does the system respond when queried columns don't exist in the schema?
- What happens when JOINs would return ambiguous column names?
- How are NULL values in aggregated contributor data handled?
- What happens when timezone conversion fails or timezone is missing?

## Requirements *(mandatory)*

### Functional Requirements

**SQL Generation Prompt Enhancement**

- **FR-001**: SQL generation prompt MUST include explicit instructions to always return event_id, event_title, event_start_dt (human-readable format), and event_timezone for event-related queries
- **FR-002**: Prompt MUST instruct the LLM to use PostgreSQL `to_char()` and `AT TIME ZONE` functions for date/time formatting in SQL output (e.g., `to_char(e.start_dt AT TIME ZONE e.timezone, 'Month DD YYYY, HH12:MI AM')`) to produce human-readable intermediate data for subsequent natural language summarization
- **FR-003**: Prompt MUST provide SQL template examples for common query patterns (events, contributors, attachments, vector search)
- **FR-004**: Prompt MUST explicitly state that date comparisons should use PostgreSQL functions (CURRENT_DATE, NOW()) rather than assuming the current date
- **FR-005**: Prompt MUST include detailed foreign key relationship hints to guide proper JOINs (e.g., "events.id is equivalent to contributions.event_id")
- **FR-006**: Prompt MUST specify using STRING_AGG or similar aggregation when combining multiple contributor rows to avoid result duplication

**Vector Search Prompt Enhancement**

- **FR-007**: When a document content query is classified, the generated SQL MUST include `ORDER BY embeddings <=> :query_vector` pattern for similarity search against `plugin_assistant.extracted_documents`
- **FR-008**: System MUST support parameterized `:query_vector` placeholder that is substituted with the actual embedding vector at execution time
- **FR-009**: Vector search prompt MUST clearly state that `<=>` operator returns a float similarity score and MUST NOT be used in WHERE clause for boolean comparison
- **FR-010**: SQL generation prompt MUST include the `extracted_documents` vector search template so LLM knows when and how to include vector similarity in queries

**Classification Enhancement**

- **FR-011**: Classifier MUST recognize document/attachment/file/material keywords to route to appropriate query pattern
- **FR-012**: Classifier MUST distinguish between "event metadata queries" vs "document content queries" vs "hybrid queries"

**Guardrail Review**

- **FR-013**: System MUST maintain existing guardrail restrictions (CTEs, subqueries, window functions) and document rationale; CTEs remain blocked to minimize attack surface and prompt complexity
- **FR-014**: System MUST provide alternative query patterns (JOIN-based) in the prompt when restricted syntax would otherwise be optimal
- **FR-015**: Error messages for guardrail violations MUST be user-friendly and suggest alternatives where possible

**Schema Context Enhancement**

- **FR-016**: Schema prompt MUST include suggested table aliases (e.g., e for events.events, c for contributions, p for persons)
- **FR-017**: Schema prompt MUST include sample JOIN conditions for common table combinations as reference examples
- **FR-018**: Prompt MUST highlight which columns are commonly needed for context (description, venue_name, room_name, address) even if not explicitly requested

**Result Formatting**

- **FR-019**: Results containing date/time fields MUST be formatted in human-readable form with timezone indication
- **FR-020**: Results containing contributor data MUST be aggregated and presented in a structured, readable format

### Key Entities

- **SQL Generation Prompt Template**: The primary prompt template used to instruct the LLM on generating SQL queries. Contains rules, SQL examples, schema context placeholders, and formatting instructions.
- **Query Classification Prompt**: Prompt for classifying user questions into intents (event_query, contribution_query, speaker_query, attachment_query, document_query) and extracting entities.
- **Schema Context**: Database schema information including tables, columns, data types, relationships, and JOIN hints rendered into the prompt.
- **Vector Search Prompt**: Specialized prompt instructions for pgvector similarity search with correct operator usage patterns.
- **Guardrail Rules**: Security and safety constraints on generated SQL patterns, including allowlisted tables and forbidden keywords.
- **Result Format Prompt**: Instructions for the LLM to summarize query results in natural language while preserving key data points.

- **SC-002**: Multi-table JOIN queries succeed without manual correction in 90% of cases

- **SC-005**: Guardrail violation messages are actionable and suggest alternatives in all cases

## Clarifications

### Session 2026-01-19

- Q: What date/time format should event results use by default? → A: The `to_char()` format (`'Month DD YYYY, HH12:MI AM'`) is for SQL query output only; users provide natural language time references, and final responses are in natural language
- Q: Should the CTE (WITH clause) restriction be relaxed? → A: Keep blocked; provide JOIN-based alternatives in prompt instead
- Q: How should hybrid queries (requiring both SQL and vector search) be handled? → A: **ARCHITECTURE CLARIFICATION**: Vector search should be part of the LLM-generated SQL query (using `embeddings <=> :query_vector` with parameterized vector), NOT a separate RAG retrieval step. Current implementation has two paths (RAGService + NL2SQL); target architecture unifies them so the LLM generates SQL that may include vector similarity when appropriate.

## Assumptions

- The reference prompt patterns have been validated in production use and represent proven best practices for this domain
- PostgreSQL 14+ with pgvector extension is the target database environment
- The LLM (GPT-4 or similar) can follow detailed SQL generation instructions when properly prompted with examples
- Current conversation history integration from Feature 012 is functional and can be leveraged for co-reference resolution
- Schema YAML file (`available_tables.yaml`) contains accurate and complete table/column information
- Current security guardrails (no DDL, no DML, SELECT-only) remain necessary and will be preserved
- The `plugin_assistant.extracted_documents` table exists with an `embedding` column of vector type for similarity search
- Date/time formatting in SQL (`to_char()`) produces structured output for the LLM to interpret; final user-facing responses are rendered in natural language by the result formatter
- **ARCHITECTURE NOTE**: This feature unifies vector search into the NL2SQL-generated SQL queries. The LLM will generate SQL that may include `embeddings <=> :query_vector` when appropriate. The executor must support parameterized vector substitution. This differs from the current implementation where RAGService performs a separate retrieval step.
